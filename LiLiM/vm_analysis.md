## EV_AOSV2_INDEX — 容器格式

- 证据等级：**derived**
- 来源：ArcAOS.cs `Aos2Opener.TryOpen` 与本样本字节交叉验证。
- 布局：

```text
0x000  i32  签名，恒为 0（v1 此处为文件名首字节，非零）
0x004  u32  base_offset       本样本 0x18A9
0x008  i32  index_size        本样本 0x1798
0x111  索引区起点，条目步长 0x28
       +0x00  char[0x20]  名字，NUL 结尾，CP932
       +0x20  u32         相对 base_offset 的偏移
       +0x24  u32         大小
```

- 交叉验证：`index_size / 0x28 = 151` 为整数；`0x111 + 0x1798 = 0x18A9` 恰等于
  `base_offset`，即索引区末尾与数据区起点相接。151 个名字全部可按 CP932 解码且无空名。
- 反例检查：首 4 字节非零时按 v1 解析（本样本不适用，代码保留该分支的拒绝路径）。
- 头部 0x00C–0x110 除 `0x00C..0x013` 存字符串 `scr.aos` 外全为零；该区间原样保留
  （`R_HEADER`，rewrite_policy=rebuild 但内容逐字节复制）。

## EV_AOSV2_CONTIGUOUS — 条目首尾相接，无填充无校验

- 证据等级：**observed**
- 方法：按索引顺序核算 `offset + size` 与下一条目 `offset`。
- 结果：151 个条目，**0 处缺口、0 处重叠**，偏移单调递增，末条目终点
  `0x1ADE85` 恰等于文件长度。
- 推论（回封的前提）：数据区无对齐 padding、无归档级校验和，故变长回封只需
  按新长度依次排布并回填索引的两个字段。对齐取 1。
- 反面约束：正因为无 padding，`in_place` 的容量不可由「下一条目起始偏移相减」推得
  额外余量——相减所得恰等于本条目大小，无冗余（§6.0.2 第三种来源在此为紧确值）。

## EV_HUFFMAN_STREAM — .scr 的 Huffman 封装

- 证据等级：**observed**
- 来源：ArcAOS.cs `OpenEntry` 对 `.scr` 走 `HuffmanStream`；前 4 字节为解压后长度。
- 位流规格（由本样本实测确定并逐条验证）：

```text
条目 +0x00  u32  解压后长度
条目 +0x04       位流起点，MSB-first
树编码（前序）：读 1 位
  1 → 内部节点，随后紧跟左子树、右子树；内部节点编号自 256 递增
  0 → 叶节点，随后 8 位为字节值
解码：自根起每读 1 位向左（0）/ 右（1）下行，至叶输出该字节，重复至解压长度
```

- 交叉验证：149 个 `.scr` 全部解压成功，且**位流恰好被消耗完**
  （消耗字节数 == `size - 4`，149/149 命中）——若位序或树编码有误，
  不可能在全部样本上同时长度正确且无残余。
- 解压结果全部可按 CP932 严格解码，无一处失败（`errors` 未设兜底，§4.4）。
- 逆变换：本工具自行构造规范 Huffman 树（频次升序、同频按字节值升序、
  合并结果插回队尾），故同一输入必得同一位流——渲染确定性的前提。
  **注意**：重压缩位流与原始位流不必逐字节相同（原始编码器的建树策略未知），
  因此零编辑回封走「原样复制存储字节」路径，不经重压缩；只有内容改变的条目才重压缩。
  这是 `roundtrip_identity` 在本方言下成立的方式。
- 未决：原始编码器的建树细节。不影响正确性——解压是确定的，压缩只需自洽可解。

## EV_SCR_PLAINTEXT — 脚本层为明文行序列

- 证据等级：**observed**
- 解压后内容为 CP932 文本，`\r\n` 分行。149 个文件的 `\r` / `\n` 计数均相等
  （各 110,166），无孤立 CR/LF。
- 每个文件末尾恒有一个空行（尾部 `\r\n`）；129 个以 `0d 0a 0d 0a` 结尾，
  20 个以 `…END\r\n` 结尾。该性质记为 `trailing_terminator` 并在重建时复原。
- 控制字节统计：除 `\r` `\n` `\t` 外，**0x00–0x1F 全部为 0 次**。故正文中不存在
  需要占位符的控制码；占位符机制仍然实现并校验（防止译者引入）。
- 推论：这不是字节码。**不存在指令流、不存在字符串表、不存在指针。** 文本的
  「站点」是行内的字符区间，而非文件内的偏移引用——这是本方言与典型 VM 格式的
  根本差异，也是 `join_sites` 只登记归档索引槽位的原因。

## EV_SHAPE_CONT — 对话折行续行（本作新增，全语料 1 行）

- 证据等级：**observed**
- `00_01.scr:524`：`´＿ゝ｀）－＿－）＝゜ω゜）ノ━━━！！！！』`——颜文字表情
  过长折行，续行承接上一行 `[ヨミさん]『キタ…` 的对话。
- 判定条件：排除全部结构起首字符（`[` `　` `「` `『` `ｔ`（cg_label）
  `0-9A-Za-z_%#^:` 与空白）后的剩余行。全语料仅命中该 1 行，无误吞。
- **合并为一条导出**（`continuation: True`）：续行片段不作为独立条目，而是并入
  紧邻上一物理行的正文条目，译者看到完整一句。片段各自保留
  `(lineno, col_start, col_end)`，回封时按行切回原物理行，故行结构逐字节复原
  （实测零编辑往返一致，行数不变）。
- 合并范围**只限紧邻的上一行**：中间隔任何其他形态（含空行）即失效。
  反例检查：`D_22.scr` 的信件段落（206/217/231/257 行）引号跨多个段落未闭合，
  但各段之间有空行，故不被误并——这也说明「引号未闭合」不可作为合并判据。
- 完备性不变式因此改为
  `msg == dialogue + narration + quoted_narration + dialogue_cont - merged_continuations`，
  否则正确的合并会被误报成漏抽。
- 形态报告中续行片段按**自身形态**计入 `texts`，避免 `dialogue_cont` 显示为
  「匹配了行却 0 条文本」而与 BARREN_SHAPE（真正的漏抽）混淆（§8.3）。

## EV_TEXT_CELL — 正文按 2 字节格子推进（决定译文必须全角）

- 证据等级：**observed**
- 现象：译文 `「昨天的《美神Ｍａｇａｚｉnｅ》…」`（00_02.scr idx=64）混入 1 个
  半角 `n`，游戏启动该场景时弹出宿主的 `表示文字列が不正です`，且窗口里
  `Ｍａｇａｚｉｎｅ` 显示成半角 `Magazin`、其后文字变为乱码 `鷗死鑿`——
  即从该点起后续双字节被从**奇数偏移**切开。
- 宿主证据：`恋する少女と想いのキセキ.exe` 偏移 `0x93684` 附近存有
  `表示文字列が不正です` 与 `名前表示指定が不正です` 两条错误串，说明宿主对
  显示字符串做合法性校验（未反汇编校验代码本身，故不申报 T3）。
- 语料证据（关键）：原版归档 `a8536ff6…` 的全部 `msg` / `name` / `choice`
  槽位共 **50,989 个，非双字节字符 0 个**。半角只出现在槽位**外部**
  （`[说话人]` 的方括号，成对包住 name 槽），那是宿主切分字段用的定界符。
- 结论：这三个 tag 的槽位内容必须逐字符编码为 2 字节。装回时对半角 ASCII
  自动转全角（空格 → U+3000，其余 +0xFEE0）；转换幂等，全角再转不变。
  转完仍有 1 字节字符（半角片假名、控制符等）则**拒绝装回**并列出该字符——
  那不是打字习惯问题，需要译者明确处理。
- 转换只在 `probe` 里做一处：两处都转会让 probe 数不到半角，
  预览显示的全角化条数恒为 0（实测踩过）。
- 不纳入 `misc`（资产 ID 必须保持半角）与 `ui`（窗口标题不走正文渲染，
  原文 title 本身就含半角 `Poupee de souhaits` 等）。
- 实测：当前译文 56 条含 59 个半角字符，全部可转；转换后全量装回
  `pointer-rewrite` 通过，00_02.scr 第 153 行除说话人方括号外全为双字节。

## EV_ESCAPE_STYLE — 换行与制表符的可编辑写法

- 证据等级：**observed**
- 全语料统计：正文中**字面反斜杠出现 0 次**（`\` U+005C、`￥` U+FFE5、
  `¥` U+00A5 均为 0），控制字节只有 `0D`(169,623) `0A`(169,623) `09`(22,410)。
- 因此反斜杠转义无歧义，折行条目的换行以 `\n` 呈现（而非 `{{0D:0A}}` 占位符），
  制表符为 `\t`；为保持双向闭合，字面反斜杠写作 `\\`。
  `to_display` / `from_display` 互为逆函数（往返测试锁定 10 组用例，含
  `\`、`\\n`、混合控制字节）。
- 其余不可显示字节仍走 `{{XX}}` 成组占位符（连续字节合并为
  `{{01:02}}` 而非 `{{01}}{{02}}`）。
- **无法识别的转义即报错**（`BadEscape`），不当普通字符放过：`\x`、`\N`、
  行尾单个反斜杠均被拒。
- 折行条目的换行数在导入时按**还原后**的真实换行计数比对，不按显示串——
  显示串里的 `\\n`（字面反斜杠 + n）含 `\n` 子串，按串计数会误判。
- IR 的 `text_entries.jsonl` 中 `source` 存**显示形态**（与双行文件 ○ 行逐字
  一致，供导入锚点校验），原始形态另存 `source_raw`，字节长度仍按原始算。

- `narration`：以全角空格 `　` 起首。9,859 行，缩进统计中 `　` 恰为 9,859、
  无其他缩进形态混入；同样无行尾注释。
- **人名绑定**：`method=slot-ordinal`，依据是名字与正文在同一行的固定槽位序号，
  而非相邻关系。置信度 `derived`。不存在歧义（每行至多一个 speaker 槽），
  故无 `ambiguous` 条目。虚拟名（写死在宿主里的）在本方言中不存在。
- **完备性不变式**：`msg 条数 == dialogue 行数 + narration 行数`。
  实测 143 个脚本全部成立、0 违规。该式比密度检查强：它逐文件断言每条正文都被提取。
  阳性对照：人为关掉 `narration` 的 `text_slots` 后，129/130 个剧本脚本立即报违规。

## EV_SHAPE_CHOICE — 玩家可见选项

- 证据等级：**derived**
- 112 行以 `/` 起首（缩进 0/1/2 个 tab 均有）。选项成组出现，组内末条以 `//` 结尾
  （44 条），其余 68 条为组内非末条。
- 上下文验证：选项组之后紧跟 `%sentaku = %reg`（读取选择结果的赋值），
  组之前为设置分支参数的赋值。该上下文在全部选项组中一致。
- `//` 为组终止标记，不属文本内容，故 `choice` 捕获组以 `(?P<trail>/*)$` 排除它。

## EV_TITLE_ARG — 可见的 UI 字符串参数

- 证据等级：**derived**
- 方法（**关键**，决定全部字符串字面量里哪些是文本）：把 `call` 形态的字符串
  字面量按「是否含非 ASCII 字符」筛出，再逐条核对（§8.3 阳性对照思路）。
- 本作结果：29,059 个非空字面量中，含日文的仅两类——
  `btnset` 第 1 字面量（192，选项，见 EV_SHAPE_CHOICE_BTN）与
  `title(...)` 第 0 字面量（5 处，窗口标题，全部在 title.scr）。
- 结论：`title` 第 0 参数标 `tag=ui`；`btnset` 第 1 参数标 `tag=choice`；
  其余命令的字符串参数一律 `tag=misc` + `translate_policy=frozen` +
  `tag_subtype=asset-id`（改动会破坏素材加载，故 frozen；照常导出供复核）。
- 兄弟语料历史值：19,802/19,848 命中资产 ID，未命中 46 条中唯一可见文本即
  `title(...)`，与本作结论一致。

## EV_SHAPE_COMMENT — 注释不是可见文本

- 证据等级：**derived**
- 注释内容为开发者注记（素材用途、参数含义、分支说明），**不进入游戏画面**。
- 例外（本作新增）：`#//编号「…」` 形式的选项清单见 EV_SHAPE_CHOICE_LIST——
  该子集由独立形态在 comment 之前命中并提取；其余注释（含 `#//「…」` 无编号
  注记、注释掉的命令）不产生条目。
- 副作用：8 个纯配置脚本（CheckParam CheckRoot init_spr init_var macro
  main_har title_s var）的全部非 ASCII 内容都在注释里，提取结果为 0 条——
  由 `extract_report_textless.json` 的结构证据（无字符串字面量、剥除注释后
  无非 ASCII）单列复核，实测 8 个脚本全部通过。

## EV_LABEL_XREF — 跳转目标与脚本名/标签名对应

- 证据等级：**inferred**（不足以支撑 T3，故不用于建控制流图）
- `^gsb(X)` 的 321 个不同目标中，绝大多数与归档内 `.scr` 文件名（去扩展名）同名；

## 文本发现机制与「引用连接」在本方言的形态

§3 要求文本发现只走已证明的引用连接，禁止对原始字节做正则或特征码扫描。
本方言的具体落实：

1. **不对归档字节做任何扫描。** 条目边界全部来自索引项（EV_AOSV2_INDEX）。
2. **不对解压内容做全文正则搜索。** 文本只从**行形态的命名捕获组**取得——
   行是容器解码出的结构单元（按 `\r\n` 切分，EV_SCR_PLAINTEXT），
   捕获组是该结构内已证明的槽位（EV_SHAPE_*）。这与「拿正则在二进制里捞字符串」
   的区别是：每个条目都能回答「它是哪一行的哪个槽位」，且该行的**全部**字节
   都已归属于某个形态。
3. **改写单位 = 发现单位。** `TextSlot` 同时记录 `(lineno, col_start, col_end)`，
   回封时按此三元组定位并先校验该区间内容仍等于 IR 中的 `source`，
   不匹配即拒绝（§6.3 按站点不按值）。
4. **归档级站点**：索引项的 offset / size 两个 u32 字段，共 302 个站点
   （151 条目 × 2）。变长回封只改写这些站点。
   实测：文件中另有 **3,408 处**四字节位置的值恰等于某个站点键值——
   按值改写会静默损坏它们，按站点改写不会。这正是 §6.3 的攻击面。

## 回封策略与验证

| 场景 | 策略 | 判定方向 |
|---|---|---|
| 零编辑 | `identity` | 输出与原件**逐字节相同**（实测 SHA-256 一致） |
| 译文变长/缩短 | `pointer-rewrite` | 输出**必须不同**；长度差 == 各条目变化量之和 |

变长回封实测（详见 `output/reports/repack_verdicts.json`）：
改 8 条译文加长 → +86 字节，改 8 条缩短 → −83 字节；两个方向均满足
「仅被编辑的文件内容改变，其余 149 个条目逐字节不变」、「输出可被自身重新解析」、
「覆盖率仍为 1.0」、「新文本确实出现在输出中」、「长度差可解释」。

`in_place` 在本方言下**不适用**：条目首尾相接无冗余容量（EV_AOSV2_CONTIGUOUS），
任何加长都必须重排后续条目。probe 对超长返回 `LENGTH_OVERFLOW`，
由 `auto` 选中 `pointer-rewrite`——这是最小能力原则的正常结果，不是降级。

`full-layout` 不适用：需 T3，本方言未申报。
