# Yu-Ris YSTB v300 — VM 分析与证据台账

`opcodelist.py` 里每一个方言数值的唯一真值源。每条记录该值是怎么确定的，以及证据等级：
`observed`（直接从字节或运行时观测）> `derived`（确定性解析）> `inferred`（多证据推断）>
`unresolved`（未决）。

## 使用的语料

| 编号 | 位置 | 文件数 | 状态 |
|---|---|---|---|
| `CORPUS_A` | `E:\77\ysbin_dec.zip` | 534 | 明文，原始日文，全部 cp932 |
| `CORPUS_B` | `E:\77\ysbin` | 402 | XOR 加密，随游戏发布的中文翻译补丁 |

两者都是 YSTB v300，但形态分布不同（见 `EV_SHAPE_MSG_N`）——正因如此，跨语料回归才是真正的验证，
而不是自我确认。

## 体系结构

**不申报**寄存器/堆栈细节。已证明的是**容器**与**指令索引**，这也是已申报能力所需的全部：

```
header       32 字节，不加密
inst_index   count * 4 字节      每指令一个单元：opcode、argc、2 个零字节
arg_index    argc_total * 12     每参数一个单元：meta、length、offset
arg_data     变长                参数载荷池，由上面的单元寻址
line_index   count * 4 字节      每指令对应的源码行号
```

全程小端（`EV_ENDIAN`）。

---

## EV_CONTAINER — 四段布局

- 等级：`observed`
- 证据：两个语料全部 936 个文件均满足
  `32 + inst_index_len + arg_index_len + arg_data_len + line_index_len == 文件大小`。
- 交叉验证：`inst_index_len == line_index_len == count * 4`，936 个文件全部成立。
- 反例检查：`ysc.ybn`（`YSCM`）与 `yscfg.ybn`（`YSCF`）同样是 `.ybn` 扩展名，但魔数检查不通过，
  被判定为非剧本而拒绝解析，不会被硬塞进解析流程。

## EV_ENDIAN — 字节序

- 等级：`derived`
- 证据：按小端读取头部得到 `version == 300`，且各段长度之和等于文件大小；按大端读取得到的数值
  远超文件大小。

## EV_CIPHER — 重复 4 字节 XOR

- 等级：`observed`
- 算法：每个载荷段与一个重复的 4 字节密钥异或，头部从不参与。对称，因此同一套代码既加密也解密。
- 密钥恢复：第一个参数单元的 `offset` 字段在明文中为 0，因此该位置存储的 4 字节就是密钥本身。
  `CORPUS_B` 中每个含参数的文件都给出 `0x96AC6FD3`。
- 验证：402 个加密文件全部满足 `xor(xor(data, key), key) == data`。
- **非显而易见之处**：由于头部不加密，**加密文件**同样满足「各段长度之和等于文件大小」，
  因此该条件不能用来判断是否为明文。见 `EV_PLAINTEXT_TEST`。

## EV_PLAINTEXT_TEST — 如何判断是否需要解密

- 等级：`derived`
- 判据：`sum(argc over inst_index) == arg_index_len / 12`。
- 理由：该不变式只有在指令索引为明文时才成立。实测：`CORPUS_A` 的 534 个文件原样即满足，
  `CORPUS_B` 的 402 个文件只有在 XOR 之后才满足。
- 已否决的方案：「各段长度之和等于文件大小」——加密文件同样成立，开发中采用它导致 `CORPUS_B`
  的每个文件都被误判为明文。

## EV_INST_INDEX — 指令单元

- 等级：`derived`
- 布局：`opcode:u8, argc:u8, reserved:u16`。
- 证据：936 个文件全部满足 `sum(argc) == 参数总数`——这正是「指令边界无缝无重叠地铺满整个流」的
  证明，也是本段可申报 T3 的依据。
- 交叉验证：所有文件的所有指令中，`reserved` 那两个字节恒为零。

## EV_ARG_INDEX — 参数单元

- 等级：`derived`
- 布局：`meta:u32, length:u32, offset:u32`；`meta >> 16` 是值类别，`meta & 0xFFFF` 是参数槽序号。
- 证据：排除跳转目标单元（`EV_BRANCH_TARGET`）后，每个参数区间都落在 `arg_data` 内部，
  且全部区间的并集无缺口地覆盖 `arg_data`。
- 注意：`length == 0` 的参数其 `offset` 仍有意义（是一个游标位置）。`CORPUS_B` 实测有 6,713 个
  空参数带非零 offset，因此这些字段必须原样写回，**不能**归一化为零。

## EV_META_CLASS — 值类别

- 等级：`derived`
- 观测到的类别：`0` 裸文本、`1` 与 `2` 表达式、`3` 字面量。
- 证据（`CORPUS_B` 全部文件）：类别 3 的载荷有 238,900 次以 `M` 字符串标记开头；类别 1 的载荷以
  `W`/`B`/`I`/`H` 类型标记开头；消息指令的类别 0 载荷是不带任何 token 框架的裸编码字符串。

## EV_ARG_TOKEN — 载荷内部的 token 流

- 等级：`derived`
- 布局：`tag:u8, length:u16, payload[length]`，重复直到参数末尾。
- 证据：420,363 个非裸文本参数中，420,363 个恰好框架到自身末尾。观测到的标记：
  `M W B R I H V ) = F ! + / & Z S > |`。
- 交叉验证：每个 `M` token 声明的长度都等于其后剩余载荷长度。

## EV_COMMAND_TABLE — opcode 是 YSCM 表的下标

- 等级：`observed`
- 来源：`ysc.ybn`，魔数 `YSCM`，98 个条目。格式：偏移 8 处为条目数；每个条目是一个 NUL 结尾的
  名称、1 字节参数个数，然后每个参数一个 NUL 结尾的名称加 2 字节尾随数据。解析消耗 7,877 字节
  中的 6,832 字节，恰好得到声明的 98 个条目。
- opcode 索引该表的证据：条目 0x59 是 `WORD`，是唯一一个参数中存放裸台词文本的指令；0x1c 是
  `GOSUB`，其槽 0 恒为 `es.BGM` 这类引擎符号；0x1b 是 `GO`，其参数是标签名。
- 推论：opcode 数值从不硬编码。结构逻辑引用命令**名称**，通过已加载的表解析成数值。

## EV_CALL_GOSUB — GOSUB 的槽 0 是被调用者标识

- 等级：`derived`
- 证据：`CORPUS_B` 中 78,033 处 `GOSUB` 调用点，槽 0 **全部**为字面量类别，且全部能解析成一个
  引擎符号名，共 108 个不同的被调用者（占比最高的是 `es.VoiceSetTask` 24,437 次、`ST.F` 14,467 次、
  `CW.ZXYZ` 5,634 次）。零例外、零解析失败。
- 推论：这使「调用点 → 被调用者名 → 角色」这条推导链完整可追溯，是 `EV_CHOICE_SEL_SET` 与
  `EV_SOUND_NAME` 得以按被调用者分组识别文本的前提，也是文本发现只走已证明引用连接、
  不做旁路扫描的基础。

## EV_MSG_WORD — 台词是 WORD 的裸文本参数

- 等级：`derived`
- 证据：`CORPUS_B` 中 `WORD` 指令上有 55,205 个非空的类别 0 参数；除跳转目标单元外，
  其他任何指令都没有非空的类别 0 参数。
- 交叉验证：`CORPUS_A` 给出 84,565 个这类参数，构成 55,207 条逻辑消息——物理形态不同，
  逻辑条数一致。
- 反例检查：旧实现按「首字节是 Shift-JIS 前导字节，且整串能以 cp932 解码，且含假名/汉字」猜测
  台词。以结构定义为基准衡量，该启发式在 `CORPUS_B` 漏掉了 55,205 条中的 21,066 条（38%）。

## EV_MSG_GROUPING — 一条显示消息的范围是 WORD (_ WORD)* RETURNCODE

- 等级：`derived`
- 证据：`_`（0x54）在每个语料中出现 29,358 次，且恒位于两个 `line_index` 相同的 `WORD` 指令之间；
  `RETURNCODE`（0x3e）结束该段。
- 交叉验证：按此规则分组，`CORPUS_B` 得 55,201 条、`CORPUS_A` 得 55,203 条消息，
  把多段消息折叠后与裸参数计数吻合。
- 未决：每个语料各有 4 处 `GOSUB` 打断了一个未闭合的消息段。这些情况按「结束该消息」处理并计入，
  不会被丢弃。

## EV_SHAPE_MSG_1 / EV_SHAPE_MSG_N — 消息形态

- 等级：`derived`
- `CORPUS_B`：55,205 条单段，0 条多段。
- `CORPUS_A`：29,383 条单段，25,824 条多段（2 段和 3 段，另有 6 条为 4 段）。
- 这是同一引擎两个构建之间真实存在的 L2 形态差异：翻译补丁把多段消息压平成了一个参数。
  两种形态都已声明且都被实际命中；两者都不匹配的消息会抛错，而不是返回空结果。

## EV_BRANCH_TARGET — IF / ELSE / LOOP 把跳转目标存在 length 字段里

- 等级：`derived`
- 证据：`CORPUS_B` 有 89 个、`CORPUS_A` 有 352 个参数的 `offset + length` 超出 `arg_data` 末尾。
  把这个 `length` 当作指令下标读取，**每一例**都解析到匹配的块结束指令：`IF`→`IFEND`（298）、
  `IF`→`ELSE`（43）、`ELSE`→`ELSE`（30）、`LOOP`→`LOOPEND`（43）。两个语料零例外。
- 推论：这些单元不寻址任何 `arg_data` 字节，因此被排除在字节归属之外，其字段原样写回。
- 反例检查：把该字段当作字节跨度处理，会让区间越界最多 1,506 字节，并产生虚假的覆盖重叠。

## EV_JUMP_BY_NAME — GO 的目标是标签名

- 等级：`observed`
- 证据：`CORPUS_B` 中每个 `GO` 参数要么是存放标签名的 `M` 字符串 token（如 `"A_77_OP02"`，330 个），
  要么是 `H` 表达式 token（53 个）。没有任何 `GO` 参数存放字节偏移。
- 推论：为变长文本重排 `arg_data` **无需**任何跳转重定位——这正是 full-layout 回封在已证明的
  tier 上安全的原因。

## EV_CHOICE_SEL_SET — 玩家选项

- 等级：`derived`
- 证据：93 处 `GOSUB es.SEL.SET` 调用点；被调用者槽之后的每个字面量参数存放一个选项字符串。
  每个语料各有 195 个非空选项。

## EV_SOUND_NAME — es.SE 的槽 2 存放资源名

- 等级：`derived`
- 证据：2,353 处 `GOSUB es.SE` 调用点，其槽 2 存放 `麻雀・置く`、`ドア開け２` 这类日文文本。
  它们命名的是音频资源，因此照常导出以便使用者看见，但标记为不可编辑——翻译它们会导致
  游戏找不到文件。
- 交叉验证：除台词和选项外，没有其他被调用者分组存放 CJK 文本（实测：排除 `es.SEL.SET` 与
  `es.SE` 后，零个 CJK 字面量残留）。

## EV_SPEAKER_PREFIX — 方括号内的说话者名

- 等级：`inferred`（仅用于标注）
- 证据：`CORPUS_B` 的 55,205 条消息中有 34,690 条以 `【` 开头，其中 34,686 条有闭合的 `】`
  且其后跟正文。
- 有意弱用：该切分只用于填写 `speaker=` 注释。它从不创建条目、从不改写 tag、也从不影响字节写入
  位置，因此切错也不会把文本错配到别处。

## EV_ENCODING — cp932，声明而非猜测

- 等级：`observed`
- 证据：`CORPUS_A` 全部 84,565 条台词均可按 cp932 解码。`CORPUS_B` 中 34,202 条干净解码，
  其余 21,003 条仅在特定字节对上失败（见 `EV_PRIVATE_USE`）；把那些字节对逐对解码可见，
  周围文本是 cp932 编码的中文。
- 已否决的方案：用 GBK 作为兜底编码。实测：`CORPUS_B` 中确有 20,946 条能以 GBK 解码，但结果是
  乱码——而且存在一条在 cp932 下是可读中文、在 GBK 下是乱码的字符串，证明「第一个能解码成功的
  编码」这一策略不可靠。因此编码是显式声明的参数，无自动兜底。

## EV_PRIVATE_USE — EF F0 字节对

- 等级：`observed`
- 证据：`EF F0` 在 `CORPUS_B` 的台词中出现 23,854 次，在 `CORPUS_A` 中从未出现。cp932 拒绝该字节对。
  从上下文看它恒位于分句边界，起到该补丁的换行标记作用。
- 另观测到：`81 01`–`81 0B`（合计约 85 次）。
- 处理方式：以大写字节占位符呈现（`{{EF:F0}}`），逐字节写回。其含义无需查明即可保证往返精确，
  因此保持 `unresolved` 而不做猜测。

## 窗口常量

| 名称 | 取值 | 实测最大值 | 触达上限时 |
|---|---|---|---|
| `message_scan` | 64 | 5 | `blocked` |
| `choice_slot_scan` | 32 | 9 | `blocked` |

两者都有结构性终止条件：消息扫描由 `RETURNCODE` 界定，选项扫描由参数列表界定，
因此这两个上限是安全网而非终止依据。两个语料都未触达。

## 申报的 tier 与能力

各区域的 tier，取自覆盖证书（936 个文件完全一致）：

| 区域 | Tier | 依据 |
|---|---|---|
| header | T3 | 每个字段均已识别 |
| `inst_index` | T3 | 指令边界完整，由 argc 求和证明 |
| `arg_index` | T3 | 每个单元的三个字段均已识别 |
| `arg_data`（被引用部分） | T3 | 参数索引是完整且显式的指针表，因此本段可按不同尺寸完全重建 |
| `arg_data`（未被引用部分） | T1 | 原样保留；内部结构未证明（实测：两个语料均为 0 字节） |
| `line_index` | T3 | 每指令一个 u32 |

`min_tier = T3`，因此申报的能力为 `roundtrip`、`in_place`、`pointer-rewrite` 与 `full-layout`。
能力在代码中由 tier **推导**而来，从不硬写，因此虚报在结构上不可能发生。

**未申报 T4。** 基本块、调用图与栈效应均未建立。`IF`/`LOOP` 的目标解析程度仅够把它们排除在
字节归属之外，控制流改写与指令增删不在范围内。

## 未决问题

- `EF F0` 与 `81 01`–`81 0B` 除「该补丁的换行标记」之外的确切含义。
- `sjis_ext.bin`（22 字节）未解析；它与字符扩展的关系未证明。
- 元类别 1 与 2 在结构上可区分，但语义差异未决。
- 被调用者 id 的高 16 位，以及 `V`/`Z`/`|` 三个 token 标记，均未决。
